| **Tuesday 18/08** | Move development off the shared GPU machine now that a second team's workload is destabilising it, and replace the code-tuned language model with one better suited to the policy and HR prose the assistant is actually asked about. | Replaced the code-tuned model with the general instruction-tuned model of the same size, on the reasoning that a model specialised for source code is the wrong instrument for questions about leave policy and site procedure. Removed the 20B model rejected earlier in the month for returning empty responses, recovering 15 GB. Established that the older code-tuned model cannot simply be deleted alongside it: a pre-existing company-wide tool used by several colleagues is registered against that exact model, so it is shared infrastructure rather than a leftover. Since a second model must therefore stay installed permanently, capped the model server to one *resident* model at a time — which converts a permanent 9 GB claim on a contended 16 GB card into memory that is only held while actually in use. Separately, replaced the remote-desktop workflow with an SSH tunnel: the laptop now acts purely as an editor while all computation stays on the server, which removes an entire desktop session from a machine that was running out of memory. Finally, wrote up the operational knowledge that the code does not reveal — that the model runs on a host service shared with another team's tool rather than in our own container, that the live frontend pipeline is stored in a database rather than in the repository, and that changing configuration requires the container to be recreated rather than restarted, each of which fails silently rather than raising an error. Closed two security gaps found while doing so: the administrator account's password was a literal default in the source code and therefore in the public repository, so it was rotated and the default removed in favour of a prompt; and testing from the laptop showed that the container platform publishes ports past the host firewall, leaving the databases reachable from the office network with the vector store answering unauthenticated callers. Finally, established by testing rather than by reading the code where the file-export capability actually stands, since the project notes had recorded it as a fault in how the model requests files. The model is not the problem: asked to produce a report or a spreadsheet it correctly decides to build one and supplies the contents, and the document and spreadsheet generators return valid files that reopen cleanly. Nothing delivers them to the person who asked. The frontend layer that formats each reply forwards only the answer text and the list of sources, so a generated file is built, handed back by the backend, and then discarded. That is worse than a visibly missing feature, because the model announces success: a tester is told their Word document was created and receives no file, no link and no error message. Closing it requires the file to be stored, an authenticated download address, and a link carried through into the reply. Chart generation remains unverified and depends on the same missing delivery step. One further defect surfaced in the same test run: an export request that matched the documents poorly produced no file at all and answered in Thai. |
| **Wednesday 19/08** | Build session-scoped access control for per-chat file uploads, so that a document one user attaches to a conversation cannot be retrieved by anyone else. | Delivered the capability end to end: a person can attach a file to a conversation, ask questions about it, see what they have attached, and remove it, while an administrator can review and withdraw anything held. The isolation was the point of the exercise and was demonstrated with the live model rather than argued: a second account supplying the correct conversation identifier retrieves nothing, and the same person asking in a different conversation retrieves nothing either. Chose to keep attached files in a separate store from the main document set, so that exposure is prevented by the structure rather than by every filter being written correctly — which mattered because every account on the system currently resolves to unrestricted access. Decided against expiring attachments, since a file vanishing part-way through a conversation is worse than the storage it occupies; reclamation instead compares the conversations that still exist against the files being held and removes only the difference, and refuses to act at all if that comparison looks unreliable. Two faults were found by testing rather than by review: the attached file was being crowded out by the much larger document set whenever the question was vague, which is exactly how people ask about something they have just attached, and the chat interface re-sends a conversation's entire file list on every message, which would have caused the same document to be processed repeatedly. Also corrected a defect in which one conversation's history was being read back as context inside another, and established that the file-export feature recorded as a broken model integration is nothing of the kind — the model and the file generators both work correctly and only the delivery of the finished file to the person who asked for it is missing, which is worse than an obviously absent feature because the assistant reports success. Went on to close that gap: a generated file is now stored and the reply carries a link the recipient can actually use, where a link grants one file to one person rather than access to the account. Then carried out the deliberate security testing that had been outstanding, attacking the assistant rather than reviewing it — instructions hidden inside document contents, instructions in the question, attempts to make it recite its own operating instructions, and attempts to reach another person's files through it. It failed three of those: it obeyed instructions written inside a document, printed its own instructions on request, and complied with a plain instruction to disregard its rules. All three are now fixed, and the suite went from eleven checks passing and four failing to eighteen passing and none failing. Two things are worth recording about that. The first fix appeared complete but was not, because the protection went onto the document-answering path while the disclosure attempts are handled by the general-knowledge path, leaving the fault open on the busier route. And access control held throughout, before and after — another account given the correct conversation identifier still could not read an attachment, because who may see a document is decided when documents are fetched rather than by asking the model to behave, which is the distinction between a fault of integrity and a leak of data. Finally enabled the per-conversation upload control in the interface, having held it back until both the isolation and the injection defences were demonstrated rather than merely written. Then, with the testers' documents still not delivered, turned to what the manager had asked for after the review earlier in the week. Proved rather than argued the privacy question she cared most about: from a laptop on the ordinary office network, with no credentials of any kind, the text of an ingested document could be read straight out of the vector store — because the container platform publishes every database port past the host firewall, and the vector store authenticates nobody unless it is explicitly told to. Closed it, and re-ran the same request afterwards to confirm the connection is now refused: the databases answer only the machine itself, while the chat interface and the API still answer the office, since those are the product and are meant to be reachable. The three database passwords were replaced as well, having turned out to be not merely weak but the exact example values published in the project's own repository, so that anyone able to read the code held them. Added three checks so the same situation cannot return unnoticed, including one that refuses to start the system at all on a password that appears in that example file. Removed the copy of every answer the audit log had been keeping — five hundred characters of what is, for a document question, the document's own text, held in a table nothing protects and nothing ever read back — and deleted the seven hundred and twenty-one copies already stored, while keeping the record of who asked what, which is the log's actual purpose. Made deletion mean deletion: withdrawing a document now removes the stored original from the server instead of retaining it indefinitely, a trade-off taken deliberately, since keeping the original of a file somebody has asked to have removed is precisely the outcome such a policy exists to prevent. Added the ability to change who may see a document after it has been uploaded, which is what makes the pilot workable without HR's department data at all: documents can be loaded untagged now and labelled correctly later, where previously the only way to correct a label was to upload the whole file again. Built the accuracy measurement she asked for, deliberately choosing four measures that need nobody to write out a correct answer first, and produced the project's first real figures — every question reached the right place, no question the documents cover went unanswered, and repeated answers were 99.7% alike. Stated plainly, in the tool's own output rather than only in a report, that none of this shows an answer is correct; that still needs roughly thirty questions confirmed by somebody who knows the content, which is the one part that cannot be automated. Found in the course of that work that the standard evaluation tool would have sent every question, every generated answer and every retrieved passage of company documents to an external AI service, while a comment in the same file asserted that evaluation was local; nothing had leaked, because the tool had never been able to run at all, and it now refuses to start unless the grading model is verified to be on this machine. Finally, and only because working uploads were needed in order to test the deletion change, discovered two faults that would each have stopped Thursday's first step on its own: every document upload had been failing outright, and the administrator's upload tool could not read its own settings. Both were on the main branch with the entire test suite passing throughout, and neither was visible from reading the code — what exposed them was trying to use the system. Fixed both, and added a check on the shape of the code rather than a test for the single missing piece, so that the whole category of fault is caught next time. |
